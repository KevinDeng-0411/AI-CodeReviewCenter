# CodeAware 技术选型与能力地图

> 本文回答“为什么这样升级、哪些技术现在用、哪些以后才用”。它不是实施授权；执行顺序仍以[升级总入口](README.md)为准。
>
> - 研究日期：2026-07-29
> - 个人路线决策更新：2026-07-30
> - 当前结论：先把现有 Chat/RAG 产品闭环，再交付本机 Repo-aware Read-only Agent；
>   durable/action/remote/multi-agent 只在真实需求触发后评审

## 1. 项目成熟度判断

| 成熟度 | 定义 | CodeAware |
|---|---|---|
| M0 模型 Demo | 单次 Prompt/模型调用 | 已超过 |
| M1 可用 AI 应用 | Chat、流式、RAG、记忆、结构化输出、持久化 | 当前所在，但有 C1 契约缺口 |
| M2 生产型检索应用 | 数据作用域、可验证引用、索引生命周期、评测、trace | S1、S5 的重点 |
| M2.5 本机只读 Agent | 模型选 R0 工具、知识/仓库引用、项目隔离 | S4/S5，个人默认终点 |
| M3 受控行动 Agent | durable run、sandbox、审批、回滚 | S6–S8，条件型 |
| M4 AI 研发平台 | Git/CI/IDE/MCP、远程身份、按评测拆多 Agent | S9，条件型 |

个人项目当前不追求 M3，默认完成：

```text
M1 真实闭环
  → M2 的隔离、证据和检索质量
  → M2.5 本机 Repo-aware Read-only Agent
  → 有真实瓶颈才重新评审 M3/M4
```

## 2. 当前技术栈决策

### 2.1 继续使用

| 技术 | 决策 | 原因 |
|---|---|---|
| Python 3.12 + FastAPI + Pydantic v2 | 保留 | 与现有 async AI 服务、OpenAPI 和 schema 契约匹配 |
| SQLAlchemy async + Alembic | 保留 | 当前关系真相、项目隔离、短事务和可回滚迁移都需要；高阶审计以后按触发条件扩展 |
| PostgreSQL + pgvector | 保留 | 当前规模下可同时承载关系过滤、向量和关键词召回，减少分布式复杂度 |
| Redis | 保留但限责 | 只作缓存、实时通知和未来队列 broker，不作业务真相源 |
| LangChain model/embedding adapter | 保留 | 当前 DeepSeek/Ollama 接入已建立；在 ModelGateway 后隔离供应商差异 |
| React + Vite | 保留 | 当前需要事件、Citation 和仓库浏览体验，不需要为了只读 Agent 迁移前端框架 |
| DeepSeek + Ollama bge-m3 | 保留当前默认 | 先用评测证明质量/成本瓶颈，再考虑多供应商路由 |

### 2.2 当前版本 C1–C3 才允许增加

| 能力 | 建议 |
|---|---|
| typed SSE | JSON event + 前端纯 parser，冻结 cid、delta、warning、completed/failed |
| 安全测试入口 | fail-closed wrapper 创建一次性 PG/Redis 目标并拒绝开发库；阶段证据由 manifest + 哈希验证 |
| 前端测试 | Vitest/等价单测覆盖 parser；浏览器自动化覆盖七个现有 UI 功能域，缺少环境时明确阻塞 |
| multipart | FastAPI `UploadFile/File/Form` + 明确大小/类型边界 |
| AIReadMe 快照 | allowlist 内的有界只读扫描；不做 AST、向量源码索引或 tool calling |
| 契约验证 | OpenAPI 快照 + API E2E + 前端 contract test |

这些是补齐当前产品，不是 Agent 技术栈。

### 2.3 未来按阶段增加

| 技术/能力 | 最早阶段 | 用途 | 为什么不能提前 |
|---|---|---|---|
| LangGraph | 条件型 S3 | 固定分支编排或节点 trace | 个人默认 S4 使用普通有界循环，不为框架标签增加双 runtime |
| 内部 Tool Registry | S4 | schema、risk、scope、timeout、budget | 项目隔离和稳定 port 未完成时会放大泄漏 |
| 有界行窗口代码 chunk | S5 | commit/path/line 检索 | 复用现有 Document/Chunk/pgvector，首版不建 Symbol graph |
| Tree-sitter | S5 后条件型 | symbol/reference 质量优化 | 只有代码检索评测证明行窗口不足才增加 |
| Celery/checkpoint/OTel | 条件型 S6 | 后台任务、恢复、完整 trace | 默认同步请求无此运维需求 |
| Docker sandbox | 条件型 S7 | 隔离运行模型补丁 | 默认路线不执行模型生成内容 |
| OIDC/RBAC | 条件型 S9-C | 多用户身份和 scope | 默认固定 local sentinel、禁止远程 |
| MCP | 条件型 S9-B | 外部工具互操作 | 默认三个本地 R0 代码工具已经足够 |
| 多 Agent | 条件型 S9-D | 经评测证明的上下文隔离/并行 | 单 Agent 无瓶颈数据时只有额外成本 |

## 3. 搜索/RAG 应用能力地图

高质量 AI 搜索不等于“接一个向量库”。至少包含：

| 能力 | 当前状态 | 下一闭环 |
|---|---|---|
| 数据接入 | 文本/文件上传；文件契约有缺口 | C1 修 multipart、限制和错误 |
| 文档生命周期 | Document/Chunk 父子表 | C2 验证 upsert/delete/cascade；S5 加 revision/hash |
| 权限过滤 | `project_name` 文本、全局召回 | S1 用 `project_id` 在召回前过滤 |
| 结构切分 | 文档 title/text chunk | S5 首版使用有界行窗口；评测不足再考虑 AST/symbol |
| 词法召回 | `pg_trgm similarity` | C4 在 C3 baseline 后升级为真实 BM25；不得把 FTS/pg_trgm 冒充 BM25 |
| 向量召回 | pgvector cosine | 保留；记录 index/embedding 版本和 Recall@k |
| 融合 | 已有 RRF/加权 | 用 golden dataset 调权重，不靠主观样例 |
| rerank | 未实现 | 只有 Recall@k/MRR/nDCG 显示收益时加入 cross-encoder |
| 查询改写 | 已实现、失败静默 | C1 可观测降级；简单 symbol 查询未来绕过多余 LLM |
| Citation | 当前结果缺乏统一来源 | S4 文档 citation；S5 commit/path/line |
| 评测 | 主要是单元测试 | C3 小型检索基线；后续离线+在线 trace 回流 |
| 可观测 | 无统一 AI trace | C1 事件；S4/S5 结构化工具日志；durable 触发后再评估 OTel |

### 为什么暂不换独立向量数据库

pgvector 官方明确支持与 PostgreSQL 全文搜索组合，并可用 RRF 或 cross-encoder 融合。当前没有数据证明 QPS、语料规模、过滤复杂度或召回质量已超出 PostgreSQL 能力，因此保留 pgvector。

只有以下指标持续不达标才评估 OpenSearch/Elastic/Qdrant 等：

- 在真实规模和过滤条件下 P95 超过产品门槛；
- ANN recall 与 exact baseline 差距不可接受；
- 索引构建/恢复时间不满足目标；
- 多租户过滤或混合检索已无法安全/经济实现；
- 团队具备新增服务的运维能力。

迁移前必须用同一 golden set 比较 Recall@k、MRR/nDCG、P95、成本和运维复杂度。

## 4. Agent 应用能力地图

### 4.1 什么才算 Agent

本项目采用严格定义：

- 固定应用代码先调用 RAG/Memory，模型只回答：Chat。
- 固定节点/固定边，即使使用 LangGraph：Workflow。
- 模型能在退出条件和预算内自主选择 Tool：Agent。

因此是否使用 S3 都不影响定义：S4 模型能选择只读工具后才首次成为 Agent。

### 4.2 生产 Agent 必需能力

| 能力 | 项目契约 | 阶段 |
|---|---|---|
| 工具治理 | versioned JSON Schema、risk、scope、timeout、output limit | S4 |
| 预算/终止 | max model turns、tool calls、timeout、output limit | S4 |
| 上下文工程 | 只取所需 citation/artifact，不塞全部历史和 schema | S4/S5 |
| 运行状态 | 默认只保留 Conversation/Message；需要跨进程恢复时才引入 Run | 条件型 S6 |
| 幂等恢复 | 重投递不重复消息、ToolCall、Artifact、副作用 | 条件型 S6 |
| 证据 | 最终答案只能引用本次 ToolResult 的 citation ID | S4/S5 |
| 沙箱 | 无网、最小权限、资源限制、allowlist command | 条件型 S7 |
| 人工审批 | 精确 tool/version/args/artifact/base commit/hash | 条件型 S8 |
| 身份权限 | 默认固定本地 sentinel；远程 actor/project membership 另建阶段 | S1；条件型 S9-C |
| 可观测评测 | 默认记录工具轨迹/引用；完整 Run trace 条件型增加 | S4/S5；条件型 S6/S9 |
| 回退 | 每阶段能退回前一稳定能力 | 全阶段 |

### 4.3 为什么先单 Agent

单 Agent 更容易：

- 固定预算、工具和退出条件；
- 定位是模型、检索、工具还是状态问题；
- 建立任务成功率、成本和 P95 基线；
- 保持一个审批和写入控制点。

只有 trace/eval 证明工具过载、上下文隔离或并行收益时，才进入 S9 manager-as-tools。否则多 Agent 只是更多模型调用、状态和失败组合。

## 5. 框架选择边界

### LangGraph（个人默认不采用）

它在以下条件下可能适合：

- 与现有 Python/LangChain 技术栈相邻；
- 可显式表达固定 workflow 与条件 tool loop；
- checkpoint 支持故障恢复和 HITL；
- State 可保持 JSON/ID，业务真相继续留在 PostgreSQL。

使用边界：

- 默认 S4 直接基于 S2 ReplyEngine/application ports 实现普通有界 loop。
- 只有固定分支编排、节点级 trace 等需求有证据时，才在 S2 后、S4 前评审 S3。
- S4/S5 完成后再引入 Graph 必须重写迁移卡，不能直接执行旧 S3。
- 若未来采用，Graph node 仍只调用 application port，不直接 SQL；checkpoint 不是业务审计表。

### Celery 与更重 durable workflow

默认路线不采用 Celery。只有任务超过同步 HTTP 生命周期，或已出现断线续传、后台索引、
取消/重试和 Worker 恢复的真实需求时，才评审 S6；届时任务必须启用幂等和 PG 状态。

只有任务跨多个独立服务、持续小时/天、补偿流程复杂、需要强工作流版本迁移时，再用真实数据评估 Temporal、Dapr/Restate/DBOS 类 durable execution；不得在当前版本引入。

### OpenTelemetry + Phoenix（条件型）

默认路线不安装 OpenTelemetry 或 Phoenix。只有进入条件型 S6、且结构化日志已无法定位
跨任务恢复或评测问题时，才采用开放 trace 语义；Phoenix 可作为本地可视化/评测入口，
生产是否使用其他 OTLP backend 不影响领域契约。

Trace 默认只记录 ID、版本、耗时、usage 和脱敏摘要，不默认保存完整 Prompt、源码、工具参数或 secret。

### MCP

MCP 只解决 Agent 与工具的协议互操作，不解决：

- 本地项目权限；
- Tool risk；
- 参数审批；
- 幂等和业务事务；
- prompt injection；
- sandbox。

只有原生 adapter 数量和维护成本已有证据时才评审受控 MCP client，并把外部工具映射回
内部 Registry/Policy。实施时必须重新核对 RC/GA 状态和 conformance；任何版本都固定在
adapter 后，不让 MCP transport 类型污染领域模型。

## 6. 不升级清单

下列动作当前没有收益证据：

- 把 FastAPI 改成另一 Web 框架；
- 把 React/Vite 改成 Next.js；
- 只为技术标签把 pgvector 换成专用向量库；
- 同时维护 Java/Python 两套 Agent；
- 默认路线加入 LangGraph、Celery、Phoenix、MCP 或多 Agent；
- 在没有 durable/沙箱证据时做审批或仓库写入；
- 把 `subprocess`、shell、构建或测试包装成默认 Tool；
- 直接给模型数据库 session、宿主文件路径、shell 或长期 token；
- 只看最终回答、不测数据库/文件/分支等环境结果；
- 单 Agent 未建立 eval 就做 swarm/group chat。

## 7. 方向优先级

| 优先级 | 现在/未来 | 方向 |
|---|---|---|
| P0 | 现在 | C1 修真实 Chat/上传/启动/AIReadMe 缺口 |
| P0 | 现在 | C2 七域契约、E2E、失败路径 |
| P0 | 现在 | C3 文档、OpenAPI、版本和指标冻结 |
| P1 | C3 后 | C4 PostgreSQL BM25 + pgvector RRF 检索增强 |
| P2 | 未来，需授权 | S1-lite 项目隔离 |
| P2 | 未来，需授权 | S2-lite Agent 必需分层 |
| P3 | 未来，需授权 | S4-lite/S5-lite 本机只读知识与仓库 Agent（默认终点） |
| P4 | 条件型 | S3 LangGraph 或 S6 durable Run/trace |
| P5 | 条件型 | S7/S8 sandbox、approval 与本地行动 |
| P6 | 条件型 | S9 Git/MCP/远程身份/多 Agent |
