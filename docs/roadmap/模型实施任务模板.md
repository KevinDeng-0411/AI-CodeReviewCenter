# 交给其他模型的单阶段任务模板

> 每次只复制一段任务。当前路线阶段只有 C1、C2、C3、C4、S1、S2、S4、S5；
> 当前只能从 C1 开始。S3/S6–S9 是条件型参考，未先修订路线与证据 DAG 时不能使用本模板实施。

## 1. 当前版本任务模板

```text
请只实施 CodeAware 当前版本的 <阶段>，不要实施下一阶段，也不要加入任何 Agent 能力。

工作区：<绝对路径>

开工前必须完整阅读：
1. AGENTS.md
2. docs/INDEX.md
3. docs/roadmap/README.md
4. docs/roadmap/current-release/README.md
5. docs/roadmap/current-release/<当前阶段文档>
6. docs/roadmap/证据清单与解锁规则.md
7. 该文档引用的 ADR 和前置 evidence

执行要求：
- 先检查 git status 并保留用户已有修改。
- C1 先实现并通过 fail-closed 安全测试执行器；在此之前不得直接运行 pytest、drop_all、flushdb 或 migration downgrade。
- 只用一次性 PostgreSQL/Redis 目标运行阶段基线，记录既有失败。
- 严格按阶段允许范围实现，不顺手重构或开始 Agent。
- API/schema/数据库变化同步 Alembic、OpenAPI、前端类型和测试。
- 普通测试 mock LLM/embedding；真实调用只走指定 live/integration。
- 完成阶段要求的正常、异常、边界、演示和回退验证。
- 复制 current-release/验收证据模板，生成报告和 `docs/roadmap/current-release/evidence/<阶段>/manifest.json` 引用的产物。
- 从仓库根运行 `(cd codeaware-py && uv run python scripts/validate_stage_evidence.py <阶段>)`；只认清单引用且哈希匹配的证据。
- 所有 DoD 通过后才更新 current-release/README.md 状态；否则保持未完成并记录阻塞。

最终汇报：
- 实际修改
- 测试命令与结果
- 演示结果
- 回退结果
- evidence 路径
- 是否允许进入下一阶段
```

当前领取顺序只能是：

```text
C1 → C2 → C3 → C4
```

## 2. 个人项目 Agent 任务模板

仅在 C1–C4 的 manifest 全部验证通过、状态已是 `REVIEW_UNLOCKED`，且用户之后另行授权
当前默认阶段时使用。默认能力 DAG 是 `C4 → S1 → S2 → S4 → S5`：

```text
请只实施 CodeAware personal-local-readonly 路线的 <阶段>。

开工前先验证：
- current-release C1/C2/C3/C4 evidence 全部通过；
- C3 freeze commit、C4 validated head 与当前基线差异已解释；
- 当前阶段声明的全部直接依赖 evidence 均通过；
- 用户已在这些 evidence 完成后明确授权本阶段；首次只能授权 S1。

然后完整阅读：
1. AGENTS.md
2. docs/roadmap/README.md
3. docs/roadmap/chat-to-agent/README.md
4. docs/roadmap/chat-to-agent/personal/README.md
5. docs/roadmap/chat-to-agent/personal/<当前精简阶段文档>
6. docs/roadmap/chat-to-agent/00-执行约定与公共契约.md 中本阶段使用的子集
7. docs/roadmap/证据清单与解锁规则.md
8. 直接依赖 evidence 和相关 ADR

执行要求：
- 一次只做一个阶段，不实现下一阶段的表、API、工具或 UI。
- 只实现精简卡范围；完整平台卡不能扩大本阶段 DoD。
- S1/S2/S4/S5 均保持 local-single-user、loopback-only、remote-disabled。
- Tool handler 只能通过 application read port，不直接 SQL。
- S4 不引入 LangGraph/AgentRun/checkpoint；S5 不引入 Tree-sitter、patch、shell 或仓库写入。
- 每个正常、异常、预算、权限、故障和回退场景按阶段卡验证。
- 生成报告和 `docs/roadmap/chat-to-agent/evidence/<阶段>/manifest.json`。
- manifest 必须声明 `"route_profile": "personal-local-readonly"`，依赖按能力 DAG 填写，不能伪造 S3。
- 从仓库根运行 `(cd codeaware-py && uv run python scripts/validate_stage_evidence.py <阶段>)`。
- 全部 DoD 通过后才更新路线状态。

最终汇报只能使用相应能力名称；S5 完成后最多称为“本机单用户 Repo-aware
Read-only Agent”，不能称为 Durable/Patch/Action Agent。
```

个人默认领取顺序：

```text
S1 → S2 → S4 → S5
```

## 3. 评审任务与实施任务分开

若只希望模型评审方向，任务中明确写：

```text
只读评审，不修改代码、migration、依赖或外部系统。
```

“请看看路线”“允许评审”“可以给建议”都不等于实施授权。未来 Agent 阶段必须出现“实施/修改代码”及明确阶段编号。

## 4. 禁止的宽泛任务

不要直接下达：

```text
把项目升级成 Agent
按路线全部做完
顺便上多 Agent/MCP
使用最新技术重构
```

这类任务会绕过阶段门禁。应拆成一个阶段、一个 evidence、一次验收。
