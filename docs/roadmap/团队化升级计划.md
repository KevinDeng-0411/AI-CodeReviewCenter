# CodeAware 团队化升级计划

> **背景**：项目最初是为**软件工程实验室团队**设计的——5-20 人,新人每学期轮换,团队知识需要积累和传承。当前处于本地单用户阶段,本计划定义升级到团队可用的最小路径。
>
> **设计原则**：只为实验室场景设计,不做通用多租户。每条改动都有"为什么现在不做更复杂的方案"的理由。

---

## 1. 权限模型:三句话讲清

```text
认证 → 你是谁（登录）
会话 → 你的对话历史（私有）
知识库/记忆 → 团队的资产（全员共享,谁上传的不重要）
```

| 资源 | 可见性 | 理由 |
|---|---|---|
| 知识库文档/分块 | **全员共享** | 编码规范、架构文档、项目复盘是团队资产 |
| 长期记忆 | **全员共享** | "这个项目用 PostgreSQL"对全队有用,不绑定个人 |
| 对话/消息 | **用户私有** | 每个人的提问历史和 AI 回复是个人工作记录 |
| Code Review 记录 | **全员可见** | 审计性质,谁提的、AI 给了什么建议——可追溯 |
| Unit Test 记录 | **全员可见** | 同上 |
| AIReadMe 记录 | **全员可见** | 同上 |
| Prompt 模板 | **admin 可编辑,全员可读** | 团队共享的提示词资产 |

**没有**项目管理（X-Project-ID）、没有组织/团队表——只有一个实验室团队,不需要这些。

---

## 2. 实施步骤:三阶段

### 阶段 A:认证 + 用户表（最优先）

**新增**:

```text
users
  id            UUID PK
  username      VARCHAR(50) UNIQUE NOT NULL
  password_hash VARCHAR(255) NOT NULL
  role          VARCHAR(20) NOT NULL DEFAULT 'member'  -- admin / member
  display_name  VARCHAR(100)
  created_at    TIMESTAMPTZ
```

- `POST /api/auth/login` → JWT access token（过期 24h）+ refresh token（7 天）
- `POST /api/auth/register` → admin 才能操作（实验室场景:管理员统一创建账号,不开放注册）
- 中间件 `get_current_user`:从 `Authorization: Bearer <token>` 解析 user_id,注入 request
- 不接 OAuth/GitHub/SSO——实验室内部使用,JWT 足够

**迁移**:
- 新建 `users` 表（Alembic head 0007）
- 为已有数据创建默认 admin 用户,存量会话/知识库全部关联到该用户

### 阶段 B:资源归属（改现有表）

**需要加 `user_id` 的表**（私有资源）:

| 表 | 改动 | 说明 |
|---|---|---|
| `conversations` | + `user_id FK → users` | 每个会话属于一个用户 |
| `messages` | + `user_id FK → users`（冗余,加速查询） | 消息也已归属用户 |

**不需要加 `user_id` 的表**（共享资源）:

| 表 | 不改 | 说明 |
|---|---|---|
| `documents` | 保持现有 | 全员共享 |
| `knowledge_chunks` | 保持现有 | 随 document CASCADE |
| `long_term_memories` | 保持现有 | 抽自对话,但事实本身对全员有用 |
| `prompt_templates` | 保持现有 | admin 管理,全员使用 |
| `ai_operation_records` | 保持现有（已有字段可追溯） | audit log,全员可见 |
| `ai_readme_documents` | 保持现有 | 全员可见 |

**API 变更**:
- Chat 路由:`GET /api/chat/conversations` → 只返回当前用户的会话
- Chat 路由:访问别人的 `conversation_id` → 404（不暴露"存在但无权访问"）
- Knowledge/Memory 路由:不加 user_id 过滤,全员可查

**并发 guard 升级**:
- 当前进程内 dict → PG advisory lock（`pg_try_advisory_lock(hashtext(cid))`）
- 事务提交自动释放,零额外依赖
- 不同会话仍可并行

### 阶段 C:前端 + 体验（最后）

- Login 页面（JWT 存 localStorage,axios 拦截器自动带 token）
- 顶部栏显示当前用户名 + 退出按钮
- 知识库/记忆页面标注"团队共享"提示
- Admin 页面:用户管理（创建/禁用账号,不需要删除——保留审计追溯）

## 3. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| OAuth/SSO/GitHub 登录 | 实验室内部工具,JWT 足够；外部依赖增加部署复杂度 |
| 项目管理（X-Project-ID） | 只有一个团队,项目粒度由知识库 source_type/project_name 即可区分 |
| 知识库权限（谁上传谁可见） | 和"团队知识共享"目标矛盾；需要"私人文档"会另外加 `visibility` 列 |
| 角色 RBAC 细化（viewer/editor） | admin/member 二分足够——admin 管用户+Prompt,member 用所有功能 |
| 多 worker + Redis pub/sub SSE | 先做 sticky session（nginx `ip_hash`）,真实并发上来再改 |
| 数据库分库分表 | 实验室 5-20 人规模不需要 |
| 审计日志用户行为 | 已有 `ai_operation_records`,user_id 已在阶段 B 加 |

## 5. 验证标准

完成后的验收场景:

1. admin 创建两个用户 alice 和 bob
2. alice 上传一篇知识库文档"团队编码规范"
3. bob 登录后在 Chat 中问"编码规范是什么" → 命中 alice 上传的文档（知识共享验证）
4. alice 和 bob 各自创建对话,互不可见（会话隔离验证）
5. bob 尝试访问 alice 的 conversation_id → 404
6. 未登录访问 Chat API → 401
7. 同用户同会话并发 → 409（advisory lock 验证）
8. 关闭服务后重启,所有数据完整（PG 真实性验证）

## 6. 与 Agent 路线的关系

本计划是 Agent 路线（S1-S5）之前**可选的独立升级**。两者不冲突:

- 团队化升级：让多人能使用当前 Chat/RAG 功能
- Agent 路线：让模型能自主选工具

可以先做团队化升级,再在基础上做 Agent——届时 Agent 的工具调用也在同一套认证+共享模型下运行。
