# 阶段证据清单与解锁规则

> 本文件定义 C1–C3、S1–S8 与 S9-A/B/C/D 共用的机器可校验证据。阶段文档中的勾选框和说明文字只是阅读材料；只有本规范定义的 `manifest.json` 及其引用产物可以解锁下一阶段。

## 1. 唯一证据入口

每个阶段只有一个当前有效入口：

```text
docs/roadmap/current-release/evidence/C1/manifest.json
docs/roadmap/current-release/evidence/C2/manifest.json
docs/roadmap/current-release/evidence/C3/manifest.json

docs/roadmap/chat-to-agent/evidence/S1/manifest.json
...
docs/roadmap/chat-to-agent/evidence/S8/manifest.json
docs/roadmap/chat-to-agent/evidence/S9-A/manifest.json
docs/roadmap/chat-to-agent/evidence/S9-B/manifest.json
docs/roadmap/chat-to-agent/evidence/S9-C/manifest.json
docs/roadmap/chat-to-agent/evidence/S9-D/manifest.json
```

失败尝试放在同目录的 `attempts/<run_id>/`，不得冒充有效入口。重新验收时原子替换该阶段的 `manifest.json`，并在 `supersedes_manifest_sha256` 中记录旧清单哈希。

证据目录中未被 `manifest.json` 以相对路径和 SHA-256 引用的截图、日志、报告和说明一律不计入验收。Markdown 中的 `[x]`、口头汇报、测试数量、覆盖率数字或“代码看起来已经存在”均不能单独解锁阶段。

## 2. 清单最小结构

清单使用严格 JSON，不允许注释、绝对路径、密钥、令牌或完整数据库连接串：

```json
{
  "schema_version": 1,
  "stage": "C1",
  "run_id": "20260729T120000Z-a1b2c3d",
  "baseline_commit": "<40-char sha>",
  "implementation_commit": "<40-char sha>",
  "implementation_parent": "<40-char sha>",
  "validated_head": "<40-char sha>",
  "supersedes_manifest_sha256": null,
  "dependencies": [],
  "authorization": null,
  "report": {
    "path": "report.md",
    "sha256": "<sha256>"
  },
  "environment": {
    "mode": "disposable",
    "postgres_database": "codeaware_test_<unique>",
    "redis_database": 15,
    "sandbox_or_compose_profile": "test"
  },
  "migration": {
    "heads": ["<revision>"],
    "current": ["<revision>"],
    "log": "artifacts/migration.json",
    "sha256": "<sha256>"
  },
  "openapi": {
    "path": "artifacts/openapi.json",
    "sha256": "<sha256>"
  },
  "commands": [
    {
      "id": "backend-unit",
      "cwd": "codeaware-py",
      "argv": ["uv", "run", "python", "scripts/run_tests_safe.py", "-q"],
      "exit_code": 0,
      "started_at": "<RFC3339 UTC>",
      "finished_at": "<RFC3339 UTC>",
      "stdout": "artifacts/backend-unit.log",
      "sha256": "<sha256>",
      "required": true
    }
  ],
  "checks": [
    {
      "id": "C1-A",
      "status": "passed",
      "artifacts": [
        {"path": "artifacts/C1-A.json", "sha256": "<sha256>"}
      ]
    }
  ],
  "rollback": {
    "temp_worktree": true,
    "disposable_database": true,
    "result": "passed",
    "artifact": "artifacts/rollback.json",
    "sha256": "<sha256>"
  },
  "limitations": [],
  "result": "passed"
}
```

约束：

- `implementation_parent` 必须是 `implementation_commit` 的直接父提交；`baseline_commit` 必须是其祖先。
- `validated_head` 必须包含 `implementation_commit`，且验证期间工作树无未解释修改。
- `dependencies` 必须精确列出全部直接前置阶段及当时验证的 manifest path、SHA-256 和 validated commit；C1 为空数组，其他阶段不得只写“前置已完成”。
- `report.path` 必须是 manifest 同目录下的 `report.md`，并通过 SHA-256 校验；报告不是未受约束的旁路附件。
- 验证器从 Git 历史推导“首次加入当前 manifest 的 evidence commit”，并校验其父链包含 `validated_head`；清单不自引用 evidence commit，避免循环哈希。
- 所有必需命令必须记录参数数组、工作目录、退出码、起止时间、日志路径和哈希。
- Alembic `heads` 必须唯一并等于一次性数据库的 `current`；OpenAPI 快照必须来自本次实现。
- 清单中任一必需项失败、缺失、哈希不符或命令超时，阶段结果只能是 `failed`。

## 3. 阶段专属聚合

除阶段卡的 DoD 外，清单必须包含下列 `checks[].id`：

| 阶段 | 必须聚合的子证据 |
|---|---|
| C1 | `C1-SAFE-HARNESS` 以及阶段卡的 `C1-A` 至 `C1-E` |
| C2 | `code-review`、`unit-test`、`ai-readme`、`chat`、`knowledge`、`memory`、`prompt` |
| C3 | `fresh-bootstrap`、`docs-contract`、`rollback`、`freeze-handoff` |
| S1 | `migration-scope`、`api-scope`、`retrieval-isolation`、`frontend-scope`、`rollback` |
| S2 | `behavior-parity`、`architecture-boundary`、`uow-transaction`、`rollback` |
| S3 | `dual-runtime-parity`、`graph-state`、`event-parity`、`rollback` |
| S4 | `tool-governance`、`budget-loop`、`citation-persistence`、`security-negative`、`rollback` |
| S5 | `repository-provenance`、`scanner-security`、`index-idempotency`、`tool-citation`、`ai-readme`、`rollback` |
| S6 | `outbox-replay`、`logical-idempotency`、`checkpoint-recovery`、`cancel-retry`、`observability`、`rollback` |
| S7 | `materializer-security`、`sandbox-isolation`、`authoritative-harness`、`patch-artifact`、`source-unchanged`、`rollback` |
| S8 | `action-manifest`、`approval-policy`、`git-cas-recovery`、`negative-paths`、`local-only`、`rollback` |
| S9-A/B/C/D | `adr-gate`、对应子卡专属 checks、`feature-rollback`；各自使用独立 manifest，未选择的子卡不得标完成 |

S9 子卡专属 checks：

- S9-A：`r3-approval`、`provider-idempotency`、`partial-success-reconcile`
- S9-B：`protocol-pin-conformance`、`connector-security`、`schema-resource-limits`
- S9-C：`identity-membership`、`tenant-isolation`、`remote-write-locked`
- S9-D：`paired-heldout-eval`、`safety-zero-violation`、`child-run-recovery`

每个 S9 manifest 还必须有 `selected_card: "A" | "B" | "C" | "D"`，并与 `stage` 及目录名完全一致。完成第二张子卡时新增其独立入口，不能覆盖第一张的 manifest。

C2 的 API 自动化必须覆盖七个功能域；浏览器自动化若未覆盖某一有 UI 的功能域，必须记录为阻塞而不是用三条“核心路径”替代七域验收。真实模型、浏览器或其他必需演示因环境不可用时，只能把本次结果写入 `attempts/<run_id>/` 并标为 `failed`/`limited`；不得占用阶段唯一 manifest、不得完成 C2/进入 C3，也不得解锁任何 Agent 阶段。

C3 manifest 还必须包含：

```json
{
  "gate": {
    "current_release_complete": true,
    "agent_review_allowed": true,
    "agent_implementation_authorized": false
  }
}
```

`agent_implementation_authorized` 在 C3 中必须为 `false`；首次实施授权只能发生在 C3 验证通过之后。

## 4. 验证器

C1 首先实现：

```text
codeaware-py/scripts/run_tests_safe.py
codeaware-py/scripts/validate_stage_evidence.py
```

从仓库根目录调用：

```bash
(cd codeaware-py && uv run python scripts/run_tests_safe.py -q)
(cd codeaware-py && uv run python scripts/validate_stage_evidence.py C1)
```

`run_tests_safe.py` 必须在导入 `app` 或 `pytest` 前 fail closed：

- 生成或验证一次性 PostgreSQL 测试库和迁移测试库；
- 拒绝 `ai_center`、`ai_center_py`、当前开发库及任何不带本次唯一后缀的库；
- 拒绝 Redis DB 0 和非测试专用 DB；
- 不接受 `setdefault` 覆盖保护，必须显式构造并打印已脱敏的测试目标；
- 只有安全检查通过后才能启动 pytest。

`validate_stage_evidence.py` 必须校验 JSON Schema、Git 祖先/父提交、必需检查集合、命令退出码、路径不逃逸、`report.md` 与所有产物哈希、Alembic/OpenAPI、回退报告和阶段依赖。只有 `result="passed"` 可作为有效阶段入口；`failed/limited` 只能留在 attempts。不得仅检查文件存在或复用文档勾选框。

在 C1 的安全执行器合入并验证前，**禁止直接执行 `pytest`、`Base.metadata.drop_all()`、Redis `FLUSHDB` 或迁移 downgrade**。当前 `tests/conftest.py` 使用环境变量 `setdefault` 后会 `drop_all/flushdb`，误指向开发环境会破坏数据。

## 5. 回退证据安全边界

- Git 回退只在由已验证 commit 创建的临时 worktree 中演练；不得清理、reset 或覆盖用户当前工作树。
- 数据库 upgrade/downgrade 只对本次创建的一次性数据库执行。
- 对真实开发/生产数据只生成备份、恢复和前向修复方案；不得为了取证自动 downgrade。
- 演练结束记录临时资源名称和清理结果，不在清单中记录凭据。

## 6. 两级 Agent 解锁

状态必须明确区分：

| 状态 | 条件 | 允许 |
|---|---|---|
| `FUTURE_LOCKED` | C1–C3 尚未全部通过 | 只可阅读、提出方向性意见和修改规划文档 |
| `REVIEW_UNLOCKED` | C1–C3 清单均通过，C3 freeze commit 是当前 HEAD 祖先，且 C3 允许正式评审 | 可做架构评审、补 ADR；不可改依赖、表、API 或 Agent 代码 |
| `IMPLEMENTATION_UNLOCKED:S1` | 上述条件 + 用户在 C3 完成后明确要求“实施 S1” | 只可实施 S1 |
| `IMPLEMENTATION_UNLOCKED:Sx` | 上一 S 阶段清单通过 + 用户在该证据形成后明确授权当前阶段 | 只可实施当前 S 阶段 |

授权规则：

- “看看方向”“路线没问题”“继续规划”“可以评审”不构成实施授权。
- 不接受在 C3 之前给出的预授权，也不接受一次性授权 S1–S9。
- 实施者必须在 evidence 中记录用户原话、任务引用和授权时所依据的 freeze/前置 commit；不得由模型自行补写同意。
- C3 完成后首次授权只能解锁 S1，后续每一阶段重新授权。

因此每个 S 阶段 manifest 的 `authorization` 不得为 null，最少包含：

```json
{
  "state": "IMPLEMENTATION_UNLOCKED:S1",
  "authorized_stage": "S1",
  "authorized_at": "<RFC3339 UTC>",
  "task_reference": "<不可由模型虚构的任务/会话引用>",
  "verbatim_instruction_artifact": "artifacts/user-authorization.txt",
  "verbatim_instruction_sha256": "<sha256>",
  "c3_freeze_commit": "<40-char sha>",
  "predecessor_manifest_sha256": "<C3 or prior S manifest sha256>"
}
```

验证器必须检查授权阶段与当前 stage 完全相等、授权时间晚于前置 manifest 的生成时间、前置哈希/commit 与 `dependencies` 一致。机器验证只能证明记录自洽，不能证明用户真实意图；实施者仍须在当前交互中看到明确授权，引用缺失或含糊时必须停止。

## 7. 权威边界

文档职责不同，不用一个笼统优先级掩盖冲突：

- ADR：长期领域语义和不可随阶段漂移的架构决策。
- `current-release/`：C1–C3 当前实现与验收的唯一执行权威。
- `migration/`：Java → Python 迁移历史、背景和已完成蓝图，不再直接下发当前任务。
- `chat-to-agent/00`：获得实施授权后，Agent 跨阶段类型与协议的唯一权威。
- `chat-to-agent/Sx`：仅描述当前已解锁阶段的增量和验收，不得重做 C1–C3。

发生矛盾时先停止实施：长期语义变化新增/修订 ADR；阶段细节错误修正对应阶段卡；未留决策记录前不得自行选择解释。
