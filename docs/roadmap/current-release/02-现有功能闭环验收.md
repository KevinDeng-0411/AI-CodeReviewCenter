# C2：现有功能闭环验收

> C1 修完真实缺口后，用同一套契约把现有 7 个功能域从 API、持久化到前端逐一验收。只修当前功能的失败，不顺带做 Agent 架构。
>
> **状态：已完成。** 机器验收见 [C2 Evidence](evidence/C2/report.md) 与
> [manifest](evidence/C2/manifest.json)；该结论只解锁 C3，不解锁 Agent。

## 1. 阶段结果

完成后，任何后续模型都能用一个 fail-closed 一次性 stack 和一组固定命令证明：

- 7 个功能域不是“有页面/有单测”，而是成功路径、失败路径和持久化都闭环；
- OpenAPI、前端 client、后端 schema 的字段名一致；
- 普通 CI 不花真实模型费用，release smoke 又能证明真实 DeepSeek/Ollama 可连接；
- 现有行为被一套回归测试冻结，后续重构可做等价对照。

## 2. 开工门槛

- `evidence/C1/manifest.json` 存在，且 `(cd codeaware-py && uv run python scripts/validate_stage_evidence.py C1)` 通过。
- typed SSE 已为默认协议。
- fresh bootstrap integration test 已通过。
- `run_tests_safe.py` 对开发/未知 PG、Redis 和伪造 stack identity 的拒绝测试已通过；C2 禁止回退到裸跑 pytest。
- AIReadMe 已使用安全有界的真实 snapshot。
- Git 工作区中的用户原有改动已记录并保留。

缺少任一项时不得开始 C2。

## 3. 先修已知契约缺口

C2 不是“只补测试”。先用契约测试暴露并修复以下已确认问题：

### 3.1 Code Review

- `CodeReviewRequest.prompt_template_id` 当前被传入 service 的 `conversation_id` 位置，而 service 并未使用它。
- 决策：保留这个公开字段，并让它真正选择一个 `CODE_REVIEW` 模板；未传时使用 active 模板。
- 指定模板不存在或类型不对时明确失败。
- `GET /api/code-review/records/{id}` 必须验证记录 type，不能用 UNIT_TEST id 读出错误类型。
- records 带 `project_name` 筛选时，`total` 必须使用相同筛选条件。

### 3.2 Unit Test

- records 的 `total` 与列表使用相同 `project_name` 条件。
- 结构化结果、framework、record type 和详情接口一致。
- 当前范围只是“生成并保存测试代码”，不宣称已执行测试；页面与文档必须使用准确措辞。

### 3.3 Query 参数

统一 Python API 的 snake_case：

```text
top_k
sample_code
project_name
```

当前前端分别发送 `topK`、`sampleCode`，需要改正。若根 README 的旧调用已有用户，后端可用 Pydantic/FastAPI alias 接受一版兼容参数，同时 OpenAPI 只推荐 canonical 名；兼容别名在 C3 写删除说明。

### 3.4 Prompt 版本化写入口

ADR-0005 已定义“编辑 = 新建版本并激活”，但当前 API/UI 只有 list/preview/activate。当前版本若继续称“Prompt 管理”，必须补齐：

```http
POST /api/prompts
```

请求至少包含 type、name、role_setting、template_body、review_dimensions、severity_levels；后端调用现有 `save_and_activate`，不能原地更新旧行。

要求：

- type 限定现有枚举；
- 必需占位符按 type 校验；
- 并发创建版本时使用锁/唯一约束与重试，保证 version 唯一；
- 每 type 恰一 active；
- 前端可创建新版本、预览并回滚到旧版本；
- 历史版本不可编辑或删除。

若产品决定当前版本只提供“只读查看与激活”，则必须删除“编辑/新增”承诺并为此新增 ADR；不得保持半实现状态。

## 4. 契约唯一来源

后端 Pydantic/OpenAPI 是 HTTP 契约真相，前端 TypeScript 和 README 从它校验：

- 为 `/openapi.json` 保存规范化快照，去除非确定字段后进入版本控制；
- 测试关键 endpoint 的 method、content-type、参数位置、required、schema；
- 前端 `api/types.ts` 不手写互相矛盾的字段；可引入 OpenAPI type generation，也可保留手写但必须有 contract test；
- 统一错误 envelope 和业务错误码；
- 列表 total、分页和 filter 语义写入测试。

本阶段不为了生成类型迁移整个前端数据层。

## 5. 七个功能域验收矩阵

### 5.1 Code Review

成功闭环：

```text
提交含已知风险的源码
→ 使用选定/active Prompt
→ 得到 Pydantic 结构化问题和计数
→ ai_operation_records 写 CODE_REVIEW
→ 列表按项目过滤
→ 详情与生成结果一致
```

失败/边界：

- 空源码、超长源码；
- 模板不存在/类型错误；
- LLM timeout、非 JSON、schema 字段缺失；
- 用 UNIT_TEST record id 访问详情；
- 项目过滤后的 total。

### 5.2 Unit Test

成功闭环：

```text
提交一个小函数
→ 生成指定 framework 的测试代码
→ ai_operation_records 写 UNIT_TEST
→ 列表/详情可查
```

失败/边界：

- 不支持 framework；
- 空/超长源码；
- 结构化输出错误；
- 用 CODE_REVIEW id 访问详情。

验收只断言生成质量的结构与关键内容，不声称生成代码已在项目中执行。

### 5.3 AIReadMe

成功闭环：

```text
选择 allowlist 内 fixture repo
→ 生成 snapshot
→ LLM 生成文档
→ ai_readme_documents 版本递增
→ GET 返回最新版本
```

失败/边界：

- repo 不存在、越界、symlink 逃逸；
- 空项目、超限、只含二进制；
- LLM 失败不写伪记录；
- 两次生成的 version/snapshot hash 可追踪。

### 5.4 Chat

成功闭环：

```text
Knowledge + Memory 已有数据
→ 新建同步/流式会话
→ Prompt 捕获证明三类上下文进入
→ 多轮会话、摘要、长期记忆抽取
→ 刷新继续会话
→ 删除后 PG/Redis 均清理
```

必须同时验证：

- typed SSE schema/version、顺序、空白、cid、唯一终态与 Abort；
- USER/ASSISTANT/summary 的 PG-first、Redis post-commit，以及 Redis 故障时无孤儿缓存；
- Redis message miss 回查 PG；
- summary Redis miss 回查 PG；
- RAG/Memory 降级使用正确的 context/post-turn warning；
- 并发新会话不串线，同一 cid 并发返回稳定 409；
- 不存在的 conversation_id 返回明确错误，不制造 FK 异常。

### 5.5 Knowledge

成功闭环：

```text
文本上传 + multipart 文件上传
→ Document 只存全文一次
→ KnowledgeChunk N 条
→ lexical + vector + fusion 检索
→ 删除 Document 后 chunks CASCADE
```

验证 query rewrite 失败时的明确降级、top_k 上限、空查询、文件限制、embedding 维度和检索结果来源。

当前 `pg_trgm similarity` 应准确描述为模糊关键词腿，不在本阶段宣称 BM25。

### 5.6 Memory

成功闭环：

```text
手动保存原子事实
→ VectorRecallService embedding
→ 语义召回
→ Chat 自动抽取带 conversation 来源的事实
→ 删除后不再召回
```

验证 memory_type 枚举/长度、threshold/top_k 边界、conversation 来源、无结果和 embedding 失败。

### 5.7 Prompt

成功闭环：

```text
4 类 seed 各一 active
→ 创建某 type v2
→ v1 自动 inactive
→ preview 替换正确占位符
→ activate v1 回滚
→ 仍恰一 active
```

验证并发创建/激活、错误 type、缺必需占位符、不存在 id，以及 CHAT/AI_README 不被 CODE_REVIEW 的 sample schema 污染。

## 6. 测试分层

建议新增：

```text
tests/contracts/test_openapi_contract.py
```

### 普通 CI

- Fake LLM 能按 Prompt type 返回合法结果、非法 JSON、timeout。
- Fake embedder 确定且固定 1024 维。
- 只能通过 `run_tests_safe.py` 使用本次随机一次性 PG/Redis；验证实际 SQL、约束、cascade 和缓存 fallback。
- 不调用 DeepSeek/Ollama，不依赖公网。

### Live smoke

使用 `@pytest.mark.live_eval` 或独立脚本，显式检查环境变量后运行。marker 测试也必须由 `run_tests_safe.py --live-eval` 调用，禁止直接执行 pytest：

- DeepSeek 一次 Chat/结构化输出；
- Ollama bge-m3 一次 1024 维 embedding；
- 一个小知识检索；
- 一个小 AIReadMe fixture。

Live smoke 不是每次普通 CI 的门禁，但 **C2 完成前必须至少成功一次**，并记录模型、时间、成本和脱敏输出。缺少凭据或 Ollama 时 C2 保持未完成，不得用 mocked 结果、文档说明或跳过标记代替。

### 浏览器 E2E

API 自动化与浏览器自动化边界固定如下：

| 层 | 必须覆盖 | 不要求重复 |
|---|---|---|
| API contract/integration | 七域全部成功、失败、边界、错误码及 PG/Redis/文件终态 | 浏览器渲染和交互细节 |
| 浏览器 E2E | 七个已有 UI 功能域各至少一条成功用户路径，以及能证明统一错误展示的一条可见失败路径 | 每个 LLM timeout、每个数据库约束和全部组合边界 |
| live smoke | 真实 DeepSeek/Ollama 的最小四项连通性与脱敏结果 | 七域全量 UI 回归 |

浏览器套件必须至少覆盖：

```text
Code Review：提交 fixture → 展示结构化结果
Unit Test：提交函数 → 展示生成代码且文案不宣称已执行
AIReadMe：选择 allowlist fixture → 展示真实 snapshot 生成结果
Chat：typed stream → cid/空白保真 → 刷新继续 → 可见 warning/failed
Knowledge：文本/文件上传 → 搜索 → 删除
Memory：保存 → 召回 → 删除
Prompt：创建 v2 → preview → activate 旧版本
```

浏览器 E2E 使用真实 FastAPI 路由、C1 一次性 PG/Redis 和受控 fake LLM/embedder adapter；不得用只返回预制 HTTP 的 fake backend 冒充 API/持久化闭环，也不得把真实 API key 注入浏览器。扩展 `run_tests_safe.py --browser-e2e`，由同一个安全执行器创建/验证 stack、启动后端和前端、执行 `npm run test:e2e` 并精确清理。

## 8. 可复制演示

提供两个脚本：

```text
codeaware-py/scripts/demo_c2_mocked.sh
codeaware-py/scripts/demo_c2_live.sh
```

`demo_c2_mocked.sh` 从隔离测试数据开始，逐域打印：

```text
[PASS] Code Review: result + record + filter/detail
[PASS] Unit Test: result + record + filter/detail
[PASS] AIReadMe: snapshot + version + latest
[PASS] Chat: typed SSE + cid + summary + continuation
[PASS] Knowledge: text/file + search + cascade delete
[PASS] Memory: manual/automatic + recall + delete
[PASS] Prompt: create v2 + preview + rollback
```

每一项都要查询一次数据库/Redis或后续 API，不能只看 HTTP 200。

两个脚本都从仓库根调用：

```bash
repo_root="$(git rev-parse --show-toplevel)"
cd "$repo_root"
./codeaware-py/scripts/demo_c2_mocked.sh
./codeaware-py/scripts/demo_c2_live.sh
```

`demo_c2_mocked.sh` 必须复用 `run_tests_safe.py` 的 target guard 和一次性 stack；不能清理按前缀命中的开发数据。

`demo_c2_live.sh`：

- 复用 `run_tests_safe.py` 的 target guard 和一次性 PG/Redis，只把模型/embedding adapter 切到真实依赖；
- 启动前检查 key/Ollama，不把 secret 打印到终端；
- 只用小 fixture，设置明确超时和最大 token；
- 将脱敏结果、模型名、耗时写入 manifest 引用的哈希产物与报告；
- 失败时返回非零状态，不用 mocked 结果代替。

## 10. 回退

- 每个契约兼容 alias 都写删除日期/阶段；回退时 canonical 字段不变。
- 新 Prompt 版本是 append-only，回退使用 activate 旧版本，不删除历史。
- API/browser/demo fixture 只存在于一次性 PG/Redis；数据前缀只用于断言，不作为安全隔离或清理授权。
- 代码回退在从起始 commit 创建的 detached 临时 `git worktree` 中验证，并绑定另一套一次性 PG/Redis；禁止 checkout/reset/clean 用户当前 worktree。
- migration downgrade、Prompt 约束回退和 fixture 清理只允许命中经 `stack_id` 校验的本次数据库。对真实数据只记录前向修复及备份/恢复方案。
- manifest 引用产物和报告记录 worktree commit、脱敏 stack identity、退出码和精确清理结果；任一清理失败则回退检查失败。
- 若某一功能失败，C2 保持未完成；不得把该功能从矩阵删掉来通过验收。
