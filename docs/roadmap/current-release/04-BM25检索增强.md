# C4：BM25 检索增强

> 本阶段位于 C3 当前版本冻结之后、任何 Agent 实施之前。目标是在不引入独立搜索服务、
> 不改变 Knowledge/Chat 对外契约的前提下，把当前 `pg_trgm similarity` 模糊关键词腿升级为
> 可证明的 BM25 词法召回，并继续与 pgvector 向量腿通过 RRF 融合。
>
> **当前状态：规划完成，未实施。** C3 Evidence 未通过前只能阅读和调整本文，不得安装
> PostgreSQL 扩展、修改 Compose、创建迁移或更改检索默认值。

## 1. 为什么单独设为 C4

当前实现已经具备：

```text
query rewrite
  → pg_trgm similarity 关键词候选
  → pgvector cosine 向量候选
  → RRF
  → match_type=keyword|vector|both
  → RAG context → Chat
```

这是一条真实的混合检索链路，但 `pg_trgm` 衡量字符串三元组相似度，不使用文档频率、
词频饱和或文档长度归一化，不能称为 BM25。C4 只升级词法腿和相应评测，不重做已经
闭环的文档父子表、Embedding、RRF、Query Rewrite、Chat Prompt 或 SSE。

C3 先冻结一份可回退的 Chat 版本，使 C4 能用同一 golden set 对比：

```text
C3 pg_trgm baseline
  ↔ C4 BM25 lexical
  ↔ C4 BM25 + pgvector + RRF
```

## 2. 开工门槛

- `evidence/C1/manifest.json`、`C2/manifest.json`、`C3/manifest.json` 均存在并通过
  `validate_stage_evidence.py`。
- C3 已生成固定的检索 golden set、基线指标、OpenAPI、Alembic head 和 freeze commit。
- 工作区干净；开发 PostgreSQL/Redis/Ollama 容器、volume 和数据指纹已记录。
- 所有数据库与检索测试继续只通过 `run_tests_safe.py` 使用随机一次性环境。
- 用户在 C3 Evidence 形成后明确要求实施 C4；这不构成 S1 或其他 Agent 阶段授权。

## 3. 技术选择门禁

### 3.1 不得混淆的三种方案

| 方案 | 本项目定义 | C4 结论 |
|---|---|---|
| `pg_trgm similarity` | 模糊字符串相似度 | 保留为一版回退后端，不再称 BM25 |
| PostgreSQL `ts_rank` / `ts_rank_cd` | PostgreSQL FTS 排名 | 可作实验基线，但不得命名为 BM25 |
| PostgreSQL BM25 扩展 | 使用语料统计的 BM25 排名 | C4 目标 |

默认候选为 ParadeDB `pg_search`：它支持当前 PostgreSQL 16 路线并提供 BM25 与 CJK
tokenizer。`pg_textsearch` 当前要求 PostgreSQL 17/18，会把“小型检索增强”扩大为数据库
大版本升级，因此不作为 C4 默认实现。禁止为了写出 BM25 技术标签而在应用内全表加载
语料后使用 `rank_bm25`，也禁止新增 Elasticsearch/OpenSearch 等第二真相源。

权威参考：

- [PostgreSQL FTS ranking](https://www.postgresql.org/docs/current/textsearch-controls.html)
- [pgvector hybrid search](https://github.com/pgvector/pgvector#hybrid-search)
- [ParadeDB pg_search](https://github.com/paradedb/paradedb/tree/main/pg_search)
- [ParadeDB CJK tokenizer](https://docs.paradedb.com/documentation/tokenizers/available-tokenizers/chinese-compatible)

### 3.2 C4-A 必须先证明兼容性

在随机 Compose project 和全新 volume 中完成 spike，不能直接改开发栈：

1. 保持 PostgreSQL 16，不迁移用户 volume。
2. 选择同时包含 `vector` 与 `pg_search` 的可复现镜像方案，固定版本和镜像 digest，
   不使用 `latest` 作为 Evidence。
3. 验证当前开发机架构、CI 架构、`vector(1024)`、Alembic、备份/恢复和 fresh bootstrap。
4. 创建最小 BM25 索引，确认中文、英文和代码标识符查询均产生可解释词项。
5. 比较 `chinese_compatible` 与可复现的词典 tokenizer；选择结果和理由写入 ADR 更新。
6. 若无法在当前架构稳定复现，C4 标为 blocked；不得静默退回 `ts_rank_cd` 后仍宣称 BM25。

## 4. 最小实施拆分

每个小阶段独立提交；前一阶段未通过定向测试和演示，不进入后一阶段。

### C4-A：运行时、ADR 与评测基线

交付：

- 基于 C3 freeze commit 固定 30～50 条无敏感信息的检索 golden cases，至少包含：
  - 中文精确术语；
  - 英文自然语言；
  - `snake_case`、类名、配置键和错误码等稀有标识符；
  - 只能靠语义召回的同义改写；
  - 应无结果的负例。
- 每条 case 在实现前固定 expected document/chunk id 或 relevance grade，禁止看完结果后改答案。
- 记录 C3 `pg_trgm`、vector-only、现有 fused 的 Recall@5、MRR@10、nDCG@10 与固定
  fixture 上的 warm P95。
- 完成隔离的 BM25 扩展/镜像兼容性 spike，更新 ADR-0001：当前状态仍为 pg_trgm，
  C4 成功后才切 BM25 默认值。
- 扩展 Evidence validator：加入 `C4: [C3]`，并把 S1 直接依赖改为 `S1: [C4]`。

建议提交：

```text
docs(C4-A): pin BM25 runtime and retrieval baseline
```

闭环演示输出：镜像版本/digest、扩展版本、PostgreSQL 版本、tokenizer、三组 C3 基线指标；
不输出文档全文、宿主路径或连接串。

### C4-B：BM25 词法后端与索引生命周期

交付：

- 将词法召回从 `VectorRecallService` 中拆成窄接口，例如：

```text
LexicalRecallPort
├── PgTrgmLexicalRecall    # 兼容回退
└── Bm25LexicalRecall      # C4 默认目标
```

- `VectorRecallService` 继续唯一负责 embed、pgvector 存储和向量召回；不得复制 embedding
  或 cosine SQL。
- 新 Alembic revision 只创建 C4 所需 extension/index/辅助对象，不新增重复 Document、
  Chunk 或 embedding 表。
- 索引只作用于 `knowledge_chunks.chunk_content`，Knowledge 上传、upsert、删除及
  `ON DELETE CASCADE` 后结果立即一致。
- 配置增加一个明确后端选择，例如 `RAG_LEXICAL_BACKEND=pg_trgm|bm25`；C4 验证前
  保持 `pg_trgm`，C4 Evidence 通过后默认改为 `bm25`。所有候选数、RRF k 和超时必须
  为正且有上限。
- 所有查询参数化；不得把原始 query、索引名或 project filter 拼进 SQL。
- Compose、fresh bootstrap 和 safe runner 使用同一固定 BM25 runtime；已有 volume
  只走显式兼容检查和前向迁移，不自动删除或重建。

建议提交：

```text
feat(C4-B): add PostgreSQL BM25 lexical recall
```

闭环演示：上传 → BM25 命中 → 同标题 upsert 后旧 chunk 不再命中 → 删除 Document 后
BM25/向量两腿均无结果。

### C4-C：混合融合、降级与 Chat 回归

交付：

- `HybridRetriever` 分别取得 BM25 与 vector 候选，再复用确定性的 RRF；相同 chunk
  命中两腿时仍返回 `match_type=both`。
- 保持现有 `/api/knowledge/search` 请求与响应字段、Chat Prompt 占位符和 SSE 事件不变；
  `match_type=keyword` 继续表示词法腿，内部日志额外记录
  `lexical_backend=bm25|pg_trgm`，不把索引实现泄漏为新公共枚举。
- embedding 在数据库事务外生成；BM25/向量查询使用短 session，不在模型网络调用期间
  持有事务。
- BM25 查询失败时：
  - Knowledge search 返回稳定、脱敏的检索降级信息或按冻结契约失败；
  - Chat 可退化为 vector-only 并产生 context warning；
  - 绝不把 vector-only 结果记录成 BM25 成功。
- 保留 `pg_trgm` feature rollback 至少一个阶段；没有显式配置时不得在请求间随机切换。
- 不增加 cross-encoder/LLM rerank；只有 C4 指标形成后才能另开阶段评审 rerank。

建议提交：

```text
test(C4-C): close BM25 hybrid retrieval and fallback
```

闭环演示固定展示：

```text
[C4 BM25] rare identifier → lexical hit
[C4 BM25] semantic paraphrase → vector hit
[C4 BM25] exact mixed query → both
[C4 BM25] extension unavailable → vector-only warning
[C4 BM25] pg_trgm feature rollback → compatible result
```

### C4-D：质量门禁、Evidence 与状态收口

完成相同 golden set 的三路对照：

| 路径 | 用途 |
|---|---|
| C3 `pg_trgm + vector + RRF` | 冻结基线 |
| C4 `BM25 only` | 证明词法腿真实生效 |
| C4 `BM25 + vector + RRF` | 最终默认路径 |

最低通过条件：

- C4 fused Recall@5 不低于 C3 fused baseline。
- 稀有标识符/精确术语子集的 MRR@10 严格高于 C3 `pg_trgm` baseline。
- 语义改写子集不得因 BM25 加入而低于 vector-only Recall@5。
- 固定 fixture、相同 warm-up/并发/运行次数下记录 P50/P95；若 P95 超过 C3 两倍，
  C4 保持未完成，先解释 query plan/index 使用情况。
- `EXPLAIN (ANALYZE, BUFFERS)` 的脱敏摘要证明 BM25 索引被使用；不在 Evidence 保存
  文档正文或 query secret。

正式 Evidence：

```text
docs/roadmap/current-release/evidence/C4/manifest.json
```

`checks` 必须精确为：

```text
bm25-runtime
lexical-quality
hybrid-fusion
index-lifecycle
fallback-rollback
```

建议拆成两个提交：

```text
evidence(C4): record validated BM25 retrieval
docs(C4): mark BM25 retrieval enhancement complete
```

## 6. 总演示

新增：

```text
codeaware-py/scripts/demo_c4_bm25.sh
```

脚本只能使用随机一次性 PG/Redis 和无敏感 fixture，固定执行：

```text
扩展/索引 ready
→ 导入 golden fixture
→ 输出 pg_trgm / BM25 / vector / fused 指标
→ 展示 rare identifier、semantic、both 三类查询
→ upsert/delete 索引一致性
→ BM25 故障时 vector-only warning
→ 切回 pg_trgm 的兼容回退
→ 精确清理且开发资源指纹不变
```

不要求在浏览器新增 BM25 控件；C4 是后端检索质量增强，现有 Knowledge/Chat 页面只做
回归验证。

## 7. 回退

- 运行时优先把 `RAG_LEXICAL_BACKEND` 切回 `pg_trgm`，无需重建业务数据。
- schema downgrade 只在 detached worktree 与一次性数据库演练；真实数据库使用备份和
  前向修复，不自动 downgrade。
- downgrade 删除 C4 自有索引/辅助对象；除非能证明无其他使用者，不自动
  `DROP EXTENSION`。
- 镜像回退前先验证现有 volume 的 PostgreSQL major、extension catalog 和数据兼容；
  不对用户 volume 执行 `down -v`。
- 回退后重新运行 C3 检索 baseline，证明 Knowledge/Chat 仍可用。

## 8. 完成边界

- 不新增 Elasticsearch/OpenSearch/Qdrant 等服务。
- 不实现 rerank、Agent Tool、Citation、Project 隔离、仓库索引或 AST。
- 不修改 Memory 的默认纯向量策略。
- 不把 PostgreSQL FTS 或 `pg_trgm` 包装成“近似 BM25”。
- C4 Evidence 通过只形成 Agent 路线的评审前置条件；S1 仍需用户在 C4 完成后另行明确授权。
