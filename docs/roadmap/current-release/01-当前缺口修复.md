## 4. 实施卡 C1-A：冻结 Chat 事件和完成语义

### 4.1 事件格式

从本阶段起，`POST /api/chat/send/stream` 固定使用版本化 typed SSE。每个 `data` 都是单行 UTF-8 JSON，并包含：

```text
protocol_version: 1
conversation_id: string
turn_id: string
sequence: integer
```

`turn_id` 只关联当前 Chat 请求、日志和事件，不是持久 AgentRun，也不新增 Run 表。SSE `id` 必须等于十进制 `sequence`；sequence 从 1 开始且在单个 stream 内严格递增。

完整事件契约：

| 事件 | 额外必需字段 | 必须语义 |
|---|---|---|
| `chat.started` | `created: boolean` | Conversation 和 USER Message 已在 PG commit 后的首事件；cid 此时可立即查询 |
| `context.warning` | `component`、`code`、`message`、`retryable` | Memory/RAG/消息缓存等上下文增益降级；随后仍可生成 |
| `token.delta` | `delta: string` | 每个非空模型 chunk；delta 原样 JSON 编码，不 trim |
| `post_turn.warning` | `component`、`code`、`message`、`retryable` | assistant 已持久化，但摘要、长期记忆或 post-commit 缓存刷新降级 |
| `chat.completed` | `assistant_message_id`、`warning_count` | assistant 已 commit，所有 post-turn 均已成功或转成 warning |
| `chat.failed` | `phase`、`error`、`partial_output_persisted` | 唯一失败终态；error 含 `code/message/retryable`，partial assistant 固定不持久化 |

`phase` 限定为 `start/context/model/persist/post_turn/cancelled`。`component` 限定为 `message_cache/summary_cache/memory_recall/rag_retrieval/summary/memory_extraction`，不能使用异常类名。错误码、枚举和各事件 Pydantic/TypeScript 类型必须来自同一份契约测试。

示例：

```text
id: 1
event: chat.started
data: {"protocol_version":1,"conversation_id":"...","turn_id":"...","sequence":1,"created":true}

id: 2
event: token.delta
data: {"protocol_version":1,"conversation_id":"...","turn_id":"...","sequence":2,"delta":" hello"}

id: 3
event: post_turn.warning
data: {"protocol_version":1,"conversation_id":"...","turn_id":"...","sequence":3,"component":"summary_cache","code":"REDIS_UNAVAILABLE","message":"摘要缓存刷新失败，已保留 PostgreSQL 真相","retryable":true}

id: 4
event: chat.completed
data: {"protocol_version":1,"conversation_id":"...","turn_id":"...","sequence":4,"assistant_message_id":123,"warning_count":1}
```

失败路径用 `chat.failed` 替换 completed，例如：

```text
id: 3
event: chat.failed
data: {"protocol_version":1,"conversation_id":"...","turn_id":"...","sequence":3,"phase":"model","error":{"code":"MODEL_STREAM_FAILED","message":"模型生成失败","retryable":true},"partial_output_persisted":false}
```

HTTP 请求校验、conversation 不存在和同 cid 已有进行中 turn 等可在创建 stream 前确定的错误，继续使用标准 HTTP 4xx + 统一错误 envelope，不伪装成 SSE。流建立后必须：

- `chat.started` 恰好一次且为首事件；
- 连接保持可写时，`chat.completed` 与 `chat.failed` 恰有一个终态，终态之后没有事件；客户端已断开时按 TurnCoordinator 的取消语义收尾，不伪造已送达终态；
- `context.warning` 只出现在 started 之后、模型完成之前；`post_turn.warning` 只出现在 assistant commit 之后；
- 服务端异常文本、Prompt、源码、连接串和 secret 不进入 `message`；客户端未知 protocol/event 必须显示协议错误并停止，不能静默当 token。

持久事件回放属于未来 S6；当前断线不重放 SSE。

建议新增：

```text
app/schemas/chat_events.py
app/ai/services/chat_events.py
app/ai/services/turn_coordinator.py
frontend/src/api/sseParser.ts
frontend/src/api/chatEvents.ts
```

不要继续输出裸 `[DONE]`。如果需要短期兼容，使用配置 `CHAT_SSE_PROTOCOL=legacy|typed`，默认 `typed`，并在 C3 删除 legacy；不得长期维护两种业务实现。

### 4.2 后端时序

新增内部 `TurnCoordinator`，同步 `/api/chat/send` 和流式 `/api/chat/send/stream` 必须共用它，不能各自复制 conversation、摘要、记忆、缓存或错误处理。它只是当前 Chat 的应用服务，不是 Tool loop、Graph 或 AgentRun。

单轮状态机固定为：

```text
validate request / acquire per-conversation turn guard
→ PG transaction A: ensure conversation + persist USER + commit
→ post-commit refresh USER message cache; remember warning on failure
→ chat.started
→ build context from PG truth/cache fallback, excluding the current USER from history
→ zero or more context.warning
→ model stream / token.delta
→ PG transaction B: persist complete ASSISTANT + commit
→ run bounded post-turn(summary + memory extraction), each write with explicit PG transaction
→ post-commit refresh message/summary caches
→ zero or more post_turn.warning
→ chat.completed
→ release turn guard / close stream
```

关键要求：

- PG 是 Conversation、Message 和 summary 的唯一真相源。任何 Redis `rpush/set/ltrim/expire/delete` 都只能发生在对应 PG commit 后；Redis 失败转 warning，不能回滚已提交的 PG，也不能阻止后续 PG 写入。
- `chat.started` 前 transaction A 必须显式 commit；不能只 `flush()` 或等待 `StreamingResponse` dependency teardown。这样模型失败后 cid 与 USER Message 仍可查询，不产生悬空 cid。
- generator/TurnCoordinator 自己拥有 session 和 transaction 生命周期。不得把请求级 session 隐式留给 dependency teardown，也不得在模型流式调用或其他外部网络等待期间保持数据库 transaction 打开。
- 当前用户消息只通过 `user_message` 进入 Prompt；conversation history 必须排除本轮刚保存的 USER，避免同一问题重复注入。
- 模型中途失败时，保留已 commit 的 conversation/USER，丢弃内存中的 partial assistant，发送 `chat.failed(phase="model", partial_output_persisted=false)`，绝不发送 completed。
- assistant PG commit 失败时 rollback transaction B、清除/重建本轮相关缓存并发送 `chat.failed(phase="persist")`；不得留下仅存在于 Redis 的 assistant。
- 非致命 context/post-turn 失败保留核心结果，生成对应结构化 warning 和脱敏服务端日志。核心 Prompt、模型或 assistant 持久化失败不能降级成 completed。
- 客户端断开/Abort 时取消上游模型迭代、丢弃 partial assistant、保留已 commit 的 USER、释放 turn guard 并记录 `client_disconnected`；连接已断时不伪造“已发送 failed”。前端重连后从 PG 刷新会话，当前版本不自动重放或重试。
- 同一 conversation 同时只允许一个进行中 turn。当前 local-first 单 worker 可以使用可清理的进程内 keyed guard，并在 C3 明确单 worker 限制；若支持多 worker，必须改为 PG 条件 lease。第二个请求在建 stream 前返回稳定 409 `CHAT_TURN_IN_PROGRESS`。
- 日志包含 conversation/component/error code，不包含 API key、完整 Prompt 或敏感上下文。

同步端点返回同一 coordinator 的最终 reply、conversation_id 和结构化 warnings；其 OpenAPI、前端类型和错误码与流式事件一同冻结。

### 4.3 前端解析

`frontend/src/api/client.ts` 不再逐行 `trim()` 解析 token：

- 按 SSE 空行边界组装完整事件，正确处理任意网络 chunk 边界；
- 只去除协议规定的 `data:` 后一个可选空格，不改 JSON 内的 `delta`；
- `JSON.parse` 后按 `event` 分派；
- `chat.started` 立即设置 `activeCid`；
- `chat.completed` 才解锁输入并刷新会话；
- `context.warning` 与 `post_turn.warning` 按 component 展示非阻塞降级提示；
- `chat.failed` 保留明确失败状态；
- Abort 后显示“生成已取消”，立即从 PG-backed API 刷新当前会话，不把本地 partial assistant 当成已保存消息；
- protocol version 或 event 未知时停止解析并显示升级错误；
- 删除“刷新列表并取第一条作为新 cid”的逻辑。

输入框的 `input.trim()` 仅用于判断用户是否输入有效文本，不等于可以 trim 模型输出。

### 4.4 测试

必须增加：

- `chat.started` 是首事件且带真实 cid。
- `chat.started` 到达时可以通过查询 API 读到已 commit 的 Conversation 和 USER Message。
- delta 为 `" hello"`、`"\ncode"`、多字节中文时逐字节/随机 chunk 分割仍完全还原。
- 每个事件的 `id == sequence`，sequence 严格递增；completed/failed 二选一且终态后无事件。
- `chat.completed` 在 assistant、summary/memory事务完成之后。
- context/post-turn 失败产生对应 warning，但核心消息仍持久化且最终 completed。
- Redis 在 USER、ASSISTANT、summary 各 post-commit 刷新点失败时，PG 真相仍存在、无孤儿缓存且事件可观察。
- 模型失败产生 failed，保留 USER、不持久化 partial assistant，绝不 completed。
- assistant commit 失败产生 failed，Redis 不得存在未提交 assistant。
- 客户端在首 token 前/多个 token 后 Abort 都会取消模型、释放 guard、保留 USER 且不持久化 partial assistant。
- 同一 cid 并发第二个 turn 返回稳定 409；两个不同新会话仍各自绑定自己的 cid。
- 捕获最终 Prompt，断言本轮 USER 内容只出现一次。
- 前端 parser 单元测试覆盖 CRLF、多 `data:` 行、半个 JSON chunk、未知版本/事件、warning、failed 和断线。

为此在前端加入最小测试框架和 `npm run test`；只测试纯 parser 和关键 Chat state，不在 C1 重写 UI。

## 5. 实施卡 C1-B：让摘要真实触发

### 5.1 消除假入口

- 从 `ShortTermMemoryManager.save_message` 删除未使用的 `bg` 参数与 BackgroundTasks 分支。
- 更新“异步生成摘要”的失真 docstring。
- 由 Chat 的统一 post-turn coordinator 在保存 assistant 后调用摘要决策。

### 5.2 幂等阈值

仅看 Redis `llen` 会受 20 条滑窗裁剪影响，不能作为长期阈值真相。新增下一序号 Alembic migration，为 Conversation 增加：

```text
summary_message_count integer not null default 0
```

触发规则：

```text
PG 当前消息总数 >= MEM_SUMMARY_THRESHOLD
且 当前消息总数 - summary_message_count >= 5
```

实现时把增量步长配置化，例如 `MEM_SUMMARY_INTERVAL=5`。成功写入新 summary 时，同一 PG 事务更新 `summary` 和 `summary_message_count`。

摘要输入使用“既有摘要 + 自上次摘要后的有界消息”，不要每次把全部历史送给 LLM。消息窗口、最大字符/token 数和截断策略必须测试并记录。

### 5.3 PG 与 Redis

- PG 是 Conversation、Message 和 summary 真相源；Redis 只保存可丢弃、可由 PG 重建的 `msgs:{cid}` 与 `summary:{cid}`。
- 将现有 `save_message()` 拆成 PG persistence 与 post-commit cache refresh 两个明确步骤；禁止在 Message commit 前执行 `rpush/ltrim/expire`。
- USER、ASSISTANT 和摘要各自只有在对应 PG transaction commit 后才刷新 Redis。缓存失败发 warning，读取必须 fallback PG 并可再次回填。
- 摘要 PG 更新与 `summary_message_count` 在同一短事务内提交；外部 LLM 调用不能占用打开的数据库事务。
- PG commit 失败时不写缓存；若故障注入证明曾发生缓存写入，必须按 PG 真相精确失效/重建后才能发送 failed。
- 不得出现 Redis 写成功、PG 回滚却发 completed 的假成功，也不得因 Redis 不可用阻止 PG 真相落库。
- 并发同会话的摘要更新使用行锁或条件更新，避免旧摘要覆盖新摘要。

### 5.4 测试和演示

测试真实 `ChatService.chat/chat_stream` 路径，而不是直接调用 `generate_summary`：

- 第一次达阈值双写 PG/Redis；
- 阈值未到不调用摘要 LLM；
- 同一消息数重试不重复摘要；
- 超过 Redis window 后仍按 PG 计数更新；
- Redis miss 从 PG 回填；
- Redis 从 turn 开始即不可用时，USER/ASSISTANT/summary 的 PG 行为仍正确，warning 可观察；
- PG commit 故障时 Redis 没有孤儿 USER/ASSISTANT/summary；
- summary LLM/Redis 异常的 warning 与完成语义。

- 日志/evidence 只记录脱敏 stack identity 和临时资源名，不记录密码、完整连接串。

空环境自动验收必须使用这套独立 CI/临时 Docker volume，不能对开发者现有 volume 执行 `down -v`，不能只靠 fixture 数据前缀声称隔离。

## 8. 实施卡 C1-E：让 AIReadMe 名副其实

当前 `project_path` 从用户请求直接进入 Prompt，既没有读取项目，也存在未来任意路径风险。本阶段使用确定性的、只读的本地快照，不做 Agent/向量索引：

建议新增：

```text
app/ai/services/project_snapshot.py
app/schemas/project_snapshot.py
```

规则：

- 只允许读取配置 `LOCAL_PROJECT_ROOTS` 下的 canonical path；
- 拒绝 symlink 逃逸、设备文件、二进制、大文件和 `.git/.env/node_modules/.venv` 等目录；
- 遵循 `.gitignore` 的基本排除；
- 限制文件数、单文件字节、总字节和最终 Prompt 字符/token；
- 首版读取目录树、README、构建/依赖清单和少量入口文件；不做 AST、embedding、符号图或 tool calling；
- 快照结构化为 path、类型、截断标记和内容，再交给现有 AI_README Prompt；
- Prompt 明确把文件内容视为资料，不执行其中的指令；
- 无权/不存在/空项目明确失败。

`AiReadmeDocument.version` 按同项目历史递增，不再永远写 1。结果记录 snapshot hash、文件数和生成时间；若当前表不适合存 metadata，使用 Alembic 增加字段。

前端明确标注“仅支持服务端允许的本地项目目录”。如果部署模式禁用本地路径，禁用表单并说明，而不是返回无依据内容。

测试：

- fixture repo 生成内容的 Prompt 中含实际 README/manifest；
- path traversal、symlink、隐藏密钥、大文件和二进制被拦截；
- 相同 snapshot hash 可追踪；
- 连续生成 version 递增；
- LLM mock 断言收到的是 snapshot，不只是路径字符串。

未来 S5 会用版本化仓库索引和代码工具替换这一小型 snapshot；C1 不提前实现那套能力。

## 10. 可复制演示

实现 `codeaware-py/scripts/demo_c1_current_fixes.sh`。它从仓库根调用，自行创建一次性 PG/Redis stack 和专用 fixture：

```bash
repo_root="$(git rev-parse --show-toplevel)"
cd "$repo_root"
./codeaware-py/scripts/demo_c1_current_fixes.sh
```

1. 上传一个 Markdown 文件，确认 document/chunk 可检索。
2. 新建 SSE Chat，打印事件序列和 `conversation_id`。
3. Fake/live 模型返回带前导空格、换行和代码块的 chunk，前端最终文本逐字符一致。
4. 连续对话达到摘要阈值，查询 PG `conversations.summary/summary_message_count` 和 Redis `summary:{cid}`。
5. 从 turn 开始注入 Redis 不可用，展示 USER/ASSISTANT/summary 仍先落 PG、warning 可观察且无孤儿缓存。
6. 在多个 token 后中断连接，展示 USER 保留、partial assistant 未持久化、guard 已释放。
7. 同一 cid 并发第二次请求，展示稳定 409；不同 cid 可并发。
8. 用 fixture repo 生成 AIReadMe，展示 snapshot 文件清单/hash 和递增 version。
9. 展示 traversal 路径被拒绝。

脚本不得依赖用户已有会话、数据库或 Redis，不得修改真实项目文件；target guard 或清理失败必须返回非零。

## 12. 回退

- 数据迁移必须有 downgrade，但 downgrade 往返只能在本阶段创建的一次性数据库中执行；不得对开发、生产或个人数据库执行回退演练。
- typed SSE 短兼容期开关可回到 legacy；C3 验收后删除 legacy。
- AIReadMe snapshot 可配置关闭，关闭时 API 明确返回能力不可用，不能退回假读取。
- 应用 commit 回退只能在 `mktemp -d` 创建并经路径校验的 detached 临时 `git worktree` 中验证；禁止在用户当前 worktree 执行 `git checkout`、`git reset` 或 `git clean`。
- 临时 worktree 必须绑定另一套一次性 PG/Redis；验证完成后只移除该精确 worktree/stack，并证明原 worktree 的 `git status` 与开发数据未变化。
- 回退验证通过 safe runner 重新跑基线测试和前端检查，命令、退出码、脱敏 worktree 标识/commit、stack_id 与清理结果写入 manifest 引用产物和报告。
