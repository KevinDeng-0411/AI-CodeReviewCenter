## 一、首要 · 计划内缺口：短期记忆摘要生成接入 Chat（必须实现）

### 背景

ADR-0003 决策点 4 + 迁移改进④ 要求：对话达阈值后**后台生成摘要**，双写 PG `conversations.summary`（真相源）+ Redis `summary:{cid}`（缓存）；读时 Redis 优先、miss 读 PG **不从消息重算**。

### 现状（已实现但未接入）

- ✅ **已实现**：`ShortTermMemoryManager.generate_summary`（LLM 增量合并摘要 + 双写 Redis/PG + flush）、单测 `test_summary_double_write_redis_and_pg`。
- ❌ **未接入**：`save_message(cid, role, content, bg=None)` 的摘要触发条件含 `bg is not None`，而 [`ChatService`](../../codeaware-py/app/ai/services/chat.py) 调 `save_message` 从不传 `bg`，chat router 亦未注入 `BackgroundTasks` → **真实对话里摘要从不触发**，`conversations.summary` 恒空。

### 影响

长对话（>20 轮窗口）早期上下文随滑窗裁剪丢失、无摘要兜底；ADR-0003 的「miss 读 PG 摘要」路径形同虚设。短对话演示不暴露，但属计划内未完成项。

### 方案（与已落地的「对话内生记忆抽取」同模式）

1. `ChatService` 在保存 ASSISTANT 后，达 `SUMMARY_THRESHOLD`（10）且 `size % 5 == 0` 时触发 `generate_summary`。
2. **触发方式：inline，复用请求 session**（`get_db` 统一 commit）。
   - SSE：在 `[DONE]` 之后触发（客户端已解锁输入，延迟对用户隐藏，与记忆抽取一致）。
   - 同步 `/send`：返回前触发。
   - **不用 BackgroundTasks**：FastAPI 依赖 post-yield（commit）在 bg 之后执行，bg 用独立 session 读不到未提交消息；且 SSE 中 bg 在 `gen()` 内添加会晚于响应挂载、不可靠。inline 已验证可行（见记忆抽取 `8ca2709`）。
3. 抽取/摘要失败静默（增益路径，不影响主流程）。

### 验收

- 真实对话达 10 条消息后，`conversations.summary` 非空、Redis `summary:{cid}` 有值。
- `_build_context_prompt` 的 `get_context_window` 含「历史对话摘要」段。
- 单测：达阈值触发摘要双写（扩展 `test_short_term.py` 或新增集成测）。

### 涉及文件

`app/ai/services/chat.py`（触发）、`app/ai/memory/short_term.py`（`generate_summary` 已就绪）、`tests/test_short_term.py`。

## 二、可升级 / 预留演进（按触发条件择机）

### U1 前置 · 后端分层重构（为 LangGraph 铺路）

- **现状（已核实）**：`app/repositories/base.py` 定义了通用 `Repository`（CRUD，替代 Java 11 个 Mapper），但**无一 service 采用**--所有服务直接 `select()` / `session.execute()` 查 DB（chat.py 6 处、prompt.py 3 处、ai_readme.py 3 处…），repository 层为死代码；持久化逻辑散落各 service，与业务逻辑耦合。
- **问题**：`ChatService` 同时背负对话编排 + 记忆抽取触发 + 三级上下文拼装 + 会话 CRUD，职责过重；直接查 DB 使服务难测试、难替换。
- **升级**：
  1. **落地 repository 模式**：把各 service 的 `select` / `add` / `delete` 收敛到 `Repository(session, Model)`，持久化与业务分离（若不采纳则删死代码避免误导）。
  2. **拆分 ChatService**：抽出 `ConversationRepository` 与上下文构建器（`_build_context_prompt` 独立），使 `ChatService` 退化为薄编排。
- **触发**：U1（LangGraph）**之前**--图节点应是薄编排，不应背着持久化；理清分层再上图。
- **价值**：为 U1 铺路；提升可测试性/可维护性；面试可讲「重构为图编排前先理清分层」的工程节奏感。
- **涉及**：`app/repositories/`（落地或删）、`app/ai/services/chat.py`（拆分）、各 service（收敛 DB 访问）。

### U1. LangGraph 编排（ADR-0007 决策点 4）

- **现状**：Chat 走命令式 `chat()` / `chat_stream()`，三级上下文（长期记忆 + RAG + 短期记忆）拼接为线性流程。
- **升级**：将「召回 → 检索 → 生成 → 持久化」重构为 LangGraph 状态图，节点化编排；可加条件路由（是否需 RAG、是否触发工具调用），展示 Agent/Graph 能力。
- **触发**：需展示 Agent/Graph 工程深度时（面试纵深加分项）。
- **价值**：核心域 Chat 从「功能基线」升级为「Agent 编排」，是工程深度最大提升项。
- **涉及**：`app/ai/services/chat.py`（重构为图）、新增 `app/ai/graph/`。

### U2. 语义切分（按句向量相似度断点）

- **现状**：Knowledge 默认 `unstructured chunk_by_title`（结构感知，500/50，格式无关）。
- **升级**：对无结构流水文本检索质量差时，改用 LangChain `SemanticChunker`（相邻句向量相似度断点切）。
- **触发**：团队文档以无结构流水文本为主、且 `chunk_by_title` 召回率不足时。
- **价值**：条件触发的切分策略升级；成本/复杂度高（每句算向量、变长块、调阈值），结构化文档边际收益低。
- **涉及**：`app/ai/rag/semantic_chunker.py`（策略可配）。

### U3. tsvector + zhparser 真 BM25

- **现状**：关键词腿用 `pg_trgm similarity`（零分词依赖，中文友好，开箱即用）。
- **升级**：切 `tsvector` + `zhparser` 扩展做真 BM25 排序。
- **触发**：关键词精确召回精度不足、需专业全文检索时。
- **价值**：检索质量提升；代价是引入中文分词扩展依赖。
- **涉及**：`app/ai/rag/hybrid_retriever.py`、Alembic（扩展 + GIN 索引）。

### U4. Pinecone 向量存储双模式

- **现状**：仅 pgvector 内联（本地，零成本）；Python 版未保留 Java 版的 Pinecone 可选分支。
- **升级**：`ai/config.py` 加 Pinecone 分支（配置 `pinecone.api-key` 切换），统一在 `VectorRecallService` 接口下，业务代码无感。
- **触发**：向量规模达百万级、需托管向量库时。
- **价值**：扩展性；当前 pgvector 对原型/中小规模足够。

### U5. 双端契约对比 + 数据迁移归并（运营）

- **现状**：Python 端契约已对齐 README 22 端点（e2e + 序列化 bug 已修）；Java 端作回退源码保留，未实跑双端 curl。
- **升级**：正式切换前，dump/restore + 迁移文档 §7.2.3 归并——
  - 旧 `knowledge_documents` 按 title 聚合 chunk → `documents` 父子表；
  - 旧 `code_review_records` / `unit_test_records` → 带 type 灌入 `ai_operation_records`；
  - 旧 embedding UUID 列 → 重新 embed 回填内联 `Vector(1024)`。
- **触发**：正式从 Java 切换到 Python 时。
- **价值**：数据无损迁移；非代码，运营步骤。

## 三、优先级

| 优先级 | 项 | 性质 | 时机 |
|---|---|---|---|
| **P0 必须** | 摘要接入 Chat（第一节） | 计划内缺口 | 尽快，补齐 ADR-0003 / 改进④ |
| **P1 纵深** | 后端分层重构（U1 前置） | 重构 | U1 之前，理清分层再上图 |
| **P1 纵深** | U1 LangGraph 编排 | 预留演进 | 后端重构后，需展示 Agent/Graph 深度时 |
| **P2 按需** | U2 语义切分 / U3 tsvector / U4 Pinecone | 条件触发 | 检索/规模瓶颈时 |
| **P3 运营** | U5 双端对比 + 数据归并 | 运营步骤 | 正式切换前 |

> 原则：P0 是基线补全（非可选）；P1 后端重构是 U1 的前置（非可选，但属重构非新功能）；U1 及 P2–P3 为「条件触发、边际收益明确时才做」，不为升级而升级。
