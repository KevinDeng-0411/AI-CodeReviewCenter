# top_k 敏感性分析：用数据决定检索层 K 值

> 状态：✅ 已完成（2026-08-05）
> 结论：**保持 top_k=5**（不改生产代码）
> 决策记录：ADR-0012

## 背景

当前 top_k 分三层，`top_k=5` 是唯一入口值，各层按倍数放大：

```text
用户问题
  → QueryRewriter 生成 2-4 个表达
  → 每查询: HybridRetriever.search_by_vector(top_k=5*2=10)   ← 层1
      → 向量腿 limit top_k*3=30 / 词法腿 top_k=10             ← 层2
      → RRF 融合截 top_k=10
  → 多查询按 chunk id 去重
  → 排序截 top_k=5                                           ← 层3 (最终注入)
```

`top_k=5` 原是经验值。本分析用 35 条 golden cases + 真实 bge-m3 验证。

## 方法

- 扫描档位：`top_k ∈ {3, 5, 8, 10, 15}`
- 评测：生产路径 `HybridRetriever.search_by_vector`（BM25+vector RRF，segmented 列）
- 35 条 golden cases，fused R@5 / MRR@10 / 去重后实际条数 / 估算 prompt token
- 脚本：`codeaware-py/tests/eval/test_topk_ablation.py`

## 数据

|---|---|---|---|---|

| **5（当前）** | **0.986** | **0.938** | 5.00 | 1500 |
| 8 | 0.986 | 0.938 | 8.00 | 2400 |

## 决策

**保持 top_k=5**。数据三组关键证据：

1. **R@5 在 top_k=3 已饱和（0.986）**——检索质量根本不是 top_k 限制的。向量腿本就强（R@5=0.957 baseline），前 3 条已含正确答案。调大 top_k 对召回零帮助。
2. **MRR@10 无单调提升**——3/5/8 都是 0.938，10→0.910（降），15→0.952。波动是 35 条样本噪声，没有"调大 top_k 提升 MRR"的证据。
3. **token 成本线性增长**——900→4500 token。top_k=8+ 是纯浪费（token 翻倍、质量零提升）。

**为什么不降到 3**：R@5 虽饱和，但 3 条没有安全边际。真实查询比 golden 难（复合问题、模糊表达、跨文档相关），且 MRR 波动说明 3 和 5 实际可能互换——省 600 token 不值得冒险。5 是"质量够 + 成本可控 + 有冗余"的平衡。

## 关键观察维度（结论）

| 维度 | 观察 | 结论 |
|---|---|---|
| 召回饱和点 | R@5 在 k=3 即饱和 0.986 | top_k 不是召回瓶颈 |
| MRR 边际收益 | 3-15 无单调提升（噪声波动） | 调大 top_k 无质量回报 |
| 去重后实际条数 | avg 实际条数 = top_k（RRF 截断） | top_k 是硬限制 |
| prompt 成本 | 900→4500 token 线性 | k=8+ 纯浪费 |

## 后续

- 若未来 golden 扩充到 100+ 条，可重跑验证（当前 35 条不足以区分 3 vs 5 的统计差异）
- 若真实查询频繁出现"需要更多上下文"的反馈，再评估 top_k=8
