## 30 秒电梯演讲

> 「我为软件工程实验室团队做一个 AI 研发效能平台,解决三个实际问题：代码评审慢、新人培训效率低、团队知识散落没统一检索。核心是带**两级记忆和混合检索的 Chat**。
> 不是简单调 API——每条请求先进 PG 保存用户消息，再并入历史摘要、长期记忆、知识库 RAG 四类上下文，
> 通过**版本化 Prompt** 调用 DeepSeek，用**自己设计的 typed SSE 协议**（8 个事件类型）流式返回。
> 检索是 **BM25 + pgvector 向量用 RRF 融合**，我跑过 35 条 golden 基准，fused MRR=0.934。
> 所有故障都有语义——降级发 `context.warning`，核心失败发 `chat.failed`，不会悄悄吞掉错误。
> 当前是 **Chat 应用不是 Agent**，没有 LangGraph 和工具循环，但路线文档已规划到只读 Agent。」

## 架构一张图

```text
React → HTTP/SSE → FastAPI
                      ├─ TurnCoordinator (Chat 状态机 —— 核心)
                      │    ├─ ShortTermMemory (PG + Redis)
                      │    ├─ LongTermMemory (pgvector 1024-d)
                      │    ├─ RagService (查询改写 → BM25 + pgvector → RRF)
                      │    └─ PromptTemplate (PG 版本化)
                      ├─ CodeReview / UnitTest / AIReadMe (薄工具，复用基建)
                      └─ Knowledge / Memory / Prompt API

PostgreSQL 16 + pgvector + pg_search   Redis 7              Ollama (bge-m3)
  真相：消息/摘要/记忆/chunk/向量          缓存：msgs窗口/摘要   本地 embedding 1024维

DeepSeek v4-flash (via langchain-deepseek)
  流式 Chat + 摘要 + 查询改写 + 事实抽取 + 结构化输出
```

**记住这条主线**：Chat 是厚核心（状态机/事务/检索/流式/故障），其余六个模块共用 Prompt + 结构化输出 + 持久化基建，是薄工具。

## 最可能被追问的 7 个问题

### Q1：Chat 一条请求走完要几步？

**11 步，分两个 PG 事务 + 一个 LLM 调用段**：

```text
Transaction A（写 USER + 建会话）→ commit → 发 chat.started
  → 构建上下文（摘要/最近消息/长期记忆/RAG）—— 此时不在事务内
  → 调 LLM astream → 每个 chunk 发 token.delta
  → Transaction B（写 ASSISTANT）→ commit
  → post-turn：刷新 Redis + 增量摘要 + 抽取长期记忆
  → 发 post_turn.warning（如有）→ 发 chat.completed
```

**一句话**：**"提交消息 → 调模型 → 提交回答 — 两次事务，模型调用不在事务内"**。

追问"为什么不在一个事务里"：LLM 可能跑 30 秒，占着连接池 = 高并发下崩溃。
追问"摘要什么时候做"：post-turn（回答已提交后），异步推进水位线，失败不撤回回答。

### Q2：为什么自己设计 typed SSE 协议？

裸 `data: token` + `[DONE]` 有三个问题：
1. **新会话没有 cid** — `chat.started` 带真实 conversation_id
2. **`[DONE]` 不保证数据库 commit** — `chat.completed` 才代表 ASSISTANT 已提交 + post-turn 收口
3. **无法区分"降级"和"失败"** — `context.warning` vs `chat.failed` 是不同的业务语义

**我的 8 个事件类型**：`chat.started` / `context.warning` / `context.references` / `reasoning.delta` / `token.delta` / `post_turn.warning` / `chat.completed` / `chat.failed`。每个事件带 `protocol_version=1` + `sequence`（严格递增）+ `turn_id`。

**一句话**：**"让前端能从事件类型判断数据库状态，而不是猜 HTTP 状态码"**。

### Q3：RAG 为什么用 BM25 + pgvector？不是只用向量吗？

向量擅长**同义**（"缓存击穿"≈"热点 Key 失效"），BM25 擅长**词面精确**（类名、版本号、错误码）。
两类召回**互补**，用 RRF（`1/(k+rank)`，k=60）按排名融合，不依赖不可比的原始分数。

**关键数字**（35 条 golden 基准）：
- 纯向量：R@5=0.957，MRR=0.920
- BM25+向量 fused（当前）：R@5=0.957，**MRR=0.934**（比纯向量高）
- BM25 让 fused MRR 反超纯向量，实现了 **1+1>2**

**为什么 BM25 而不是 pg_trgm 糊弄**？C3 的 pg_trgm 是模糊三元组，中文精确 R@5=0.00，fused MRR=0.906 甚至**低于**纯向量的 0.920（噪声拖后腿）。C4 升级 ParadeDB pg_search 真 BM25 后，fused MRR 从 0.906 跳到 0.934。

**有没有 reranker**？**没有。评估后暂缓**（ADR-0009）。MRR 0.934 已高，reranker 引入 torch 依赖 + 0.5s 延迟，边际收益未实测。**"评估后决定不做"比"盲目加"更体现判断力**。

### Q4：记忆系统怎么设计的？

| 类型 | 是什么 | 存在哪 |
|---|---|---|
| 短期记忆 | 会话工作集：最近 20 条消息 + 增量摘要 | PG（真相）+ Redis（缓存窗口 + 摘要缓存） |
| 长期记忆 | 从对话抽取的原子事实（"用户用 FastAPI"），1024 维向量语义召回 | PG（`long_term_memories` 表，embedding 内联） |
| 知识库 | 用户上传的外部文档，按标题分块，混合检索 | PG（`documents` + `knowledge_chunks`） |

**一致性原则**：**PG commit → Redis refresh**（不是 Redis-first）。Redis 先写 + PG 回滚 = 幽灵数据。

**摘要水位线**：`summary_message_count` 只推进实际进了 Prompt 的消息数，条件更新防并发旧结果覆盖新结果。

### Q5：故障了怎么处理？

**核心原则**：核心失败 → `chat.failed`，增强失败 → `warning` + `completed`

| 故障 | 行为 |
|---|---|
| Redis 挂了 | PG 继续做真相 → `context.warning` → 正常回答 |
| RAG 检索挂了 | 不注入知识上下文 → `context.warning` → 用记忆 + 模型自身知识 |
| BM25 挂了 | 退化为纯向量（`context.warning`），不伪装 BM25 成功 |
| 模型流断了 | **保留已提交的 USER**，丢弃 partial assistant → `chat.failed` |
| 客户端断开 | 关闭上游模型流，保留 USER，释放 guard —— **不伪造 completed** |
| 摘要 LLM 挂了 | 不推进水位线 → `post_turn.warning` → 回答正常完成 |
| 同会话并发 | 返回 409，不进入模型 |

**一句话**：**"回答没丢不是运气，是两次 transaction 的显式边界保证的"**。

### Q6：你这里面的存储怎么设计的？

| 表 | 存什么 | 关键设计 |
|---|---|---|
| `conversations` | 会话 + 摘要 + 水位线 | 条件更新防并发 |
| `messages` | 完整消息历史 | role + content + 时间序 |
| `long_term_memories` | 原子事实 + 向量 | embedding 内联 Vector(1024) |
| `documents` | 文档全文 | 只存一份全文 |
| `knowledge_chunks` | 分块 + 向量 | FK CASCADE 到 document |
| `prompt_templates` | 版本化 Prompt | 部分唯一索引保 active 唯一 |

**"为什么不分库"**：单用户个人项目，PG 一把梭搞定关系数据 + 向量 + BM25 词法，省掉独立向量库的部署/认证/备份成本。

### Q7：你觉得最体现工程判断力的决定？

**三个**：

1. **评估后决定不做 reranker（ADR-0009）**：指标分清（rerank 改 MRR 不改召回）、方案明确（bge-reranker-v2-m3）、门禁写清（MRR+0.01），但 torch 依赖与 C5 约束冲突 + 0.5s 延迟削弱 SSE 首 token 快叙事 + 边际收益未实测 → **暂缓并记 ADR**。

2. **typed SSE 协议**：不是找现成库，是自己设计 8 事件类型 + sequence 校验。这个决策让前端不需要猜"这行 token 是新回答还是补上一句的后半段"。

3. **C5 元素感知序列化只改解析器不改分块器**：分块策略一行没动（还是 `chunk_by_title`），只把解析器的 `str(e.text)` 改成 Title→`#`、ListItem→`-`——**最小改动面，最大收益**（DOCX/HTML/PDF 分块从定长滑窗恢复为按标题切）。

## 10 个 ADR 各一句话

| ADR | 一句话 |
|---|---|
| 0001 | Memory（对话抽取的事实）和 Knowledge（用户上传的文档）**分两张表**，来源/粒度/生命周期不同 |
| 0002 | Document→KnowledgeChunk **父子表**（CASCADE），全文只存一次、chunk 只存碎片+向量 |
| 0003 | PG 是消息真相，Redis 是**可丢弃缓存**；PG commit → Redis refresh |
| 0004 | 短期记忆 = 工作集（PG+Redis），长期记忆 = **跨会话原子事实**（PG+向量） |
| 0005 | Prompt 是**版本化资产**，部分唯一索引保每个 type 只有一个 active |
| 0006 | 审计记录 **append-only**，不修改不删除 |
| 0007 | 八个功能域七个上下文，但**Chat 是核心域**，其余是薄工具 |
| 0008 | **元素感知序列化**：Title→`#`、ListItem→`-`，PDF 用 pdfminer 字号标题检测、扫描版拒绝 |
| 0009 | **Reranker 评估后暂缓**：方案/门禁/评估路径完整，但 torch+延迟+边际收益不支撑 |
| 0010 | Chat 加**引用（context.references）+ 思考过程（reasoning.delta）**，切 ChatDeepSeek 捕获 reasoning |

## 红黑榜：不要说错

| ❌ 错误说法 | ✅ 正确说法 |
|---|---|
| 消息先写 Redis 再落 PG | **PG 先 commit，再刷新 Redis** |
| RAG 是 pg_trgm 0.3 + 向量 0.7 | **BM25 + pgvector cosine，RRF 融合**；pg_trgm 只是回退后端 |
| 已实现 rerank | **只有 RRF 融合**，reranker 评估后暂缓（ADR-0009） |
| [DONE] 表示成功 | `**chat.completed**` 才表示提交 + post-turn 完成 |
| Chat 是 Agent | **确定性 Chat 状态机**，无 Tool loop/AgentRun |
| 思考过程可持久化 | reasoning **ephemeral**，刷新即消失 |
| 引用 = LLM 显式 cite | 展示**"参考来源"**（注入 prompt 的检索结果） |
| 用 LangGraph 编排 | **纯 Python TurnCoordinator**，无 LangGraph |
| 摘要 = 每次发全量历史 | **增量合并**，水位线 + 条件更新 |
